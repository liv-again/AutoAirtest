我建议这样定义：

**Skill 是“可复用能力包”，Agent 是“带目标与决策权的执行主体”。**

更工程化地说：**skill 解决“怎么做某类事”**，而 **agent 解决“为了达成目标，何时做什么、调用谁、如何检查结果”**。

## 1. Skills 和 Agents 的核心区别

| 维度     | Skill                                  | Agent                                                        |
| -------- | -------------------------------------- | ------------------------------------------------------------ |
| 本质     | 能力模块、操作手册、流程模板、工具封装 | 任务执行主体、决策循环、自治单元                             |
| 关注点   | “如何完成某类任务”                     | “面对目标，如何规划、执行、纠错、交付”                       |
| 自主性   | 低，通常被调用                         | 高，可以选择工具、技能、子任务、下一步                       |
| 状态     | 通常无状态或弱状态                     | 通常有任务状态、会话状态、记忆                               |
| 生命周期 | 被 agent / workflow 动态加载或调用     | 接收任务 → 规划 → 执行 → 观察 → 迭代 → 输出                  |
| 典型内容 | 指令、脚本、模板、示例、约束、资源文件 | LLM、系统指令、工具集、skills、memory、planner、guardrails、eval |
| 类比     | “插件 / SOP / 函数库 / 专家手册”       | “项目经理 + 执行者 + 调度器”                                 |

Anthropic 对 Agent Skills 的定义接近“模块化能力包”：一个 skill 可以打包 instructions、metadata，以及可选的 scripts、templates 等资源，让模型在相关任务中自动使用。([Claude 平台](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview?utm_source=chatgpt.com)) OpenAI Agents SDK 则把 agent 定义为一个配置了 instructions、tools，以及可选 handoffs、guardrails、structured outputs 等运行行为的 LLM。([OpenAI](https://openai.github.io/openai-agents-python/agents/?utm_source=chatgpt.com))

所以在项目里可以采用这个边界：

```text
Tool  = 一个可调用动作接口，例如 search_db(), send_email(), run_python()
Skill = 围绕某类任务组织起来的知识/流程/资源包，例如“写论文综述 skill”
Agent = 能理解目标、选择 skill/tool、维护状态并完成任务的执行主体
```

一个常见误区是把所有东西都叫 agent。其实很多场景只需要 **workflow + skills + tools**，不需要多个 agent。Anthropic 在 agent 架构文章里也区分了 workflows 和 agents：workflow 是预定义代码路径编排 LLM 与工具，agent 则让 LLM 动态决定流程和工具使用。([Anthropic](https://www.anthropic.com/research/building-effective-agents?utm_source=chatgpt.com))

## 2. 一个合理成熟的 Agent 应该包含哪些组件？

我认为一个生产级 agent 至少应包含下面 10 类组件。

### 1. 目标与角色定义：Identity / Mission

这是 agent 的“职责边界”。

应明确：

```text
这个 agent 负责什么？
不负责什么？
成功标准是什么？
遇到不确定性时如何处理？
是否允许自主行动？
什么时候必须请求用户确认？
```

例如：

```text
ResearchAgent：
负责检索论文、归纳方法、比较实验设置、生成调研报告。
不负责直接修改代码仓库，不负责提交实验结果。
涉及事实性判断必须给出处。
```

这一层不要写成泛泛的“你是一个聪明助手”，而应该写成**岗位说明书 + 行为边界 + 输出标准**。

------

### 2. 模型层：Model / LLM Backend

包括：

```text
主模型
备用模型
温度、上下文长度、成本策略
是否支持工具调用
是否支持结构化输出
是否支持多模态输入
```

成熟系统里，agent 不应该和某一个模型强绑定。最好把模型作为可替换 backend：

```text
Agent = Policy + Memory + Tools + Skills + Runtime
Model = 可插拔推理引擎
```

这样后续可以做模型切换、成本优化、A/B 测试和降级策略。

------

### 3. 指令系统：System Prompt / Policy

这是 agent 的“操作规程”。

通常包括：

```text
角色定义
任务范围
推理与执行策略
工具使用规则
输出格式
安全边界
失败处理方式
引用与证据规则
```

例如一个代码开发 agent 的系统指令里应该规定：

```text
修改代码前先理解项目结构
优先最小改动
运行测试
不要改无关文件
失败时报告具体错误
涉及破坏性操作必须请求确认
```

这部分和 skill 的区别在于：**agent 指令是长期稳定的行为准则；skill 指令是特定任务的可加载能力包。**

------

### 4. 工具层：Tools

Tools 是 agent 能执行真实动作的接口。

例如：

```text
文件读写
代码执行
数据库查询
搜索引擎
邮件发送
日历操作
API 调用
向量检索
仿真程序
实验脚本
```

工具必须有清晰 schema：

```text
name
description
input schema
output schema
权限等级
是否有副作用
失败模式
调用成本
```

成熟实践里，tool 不应该只是“函数暴露给模型”。它还应该带权限控制、参数校验、日志记录、错误恢复和安全策略。

------

### 5. Skills 层：可复用能力包

Skill 适合封装某类重复任务的最佳实践。

例如：

```text
paper-survey-skill/
  SKILL.md
  templates/
    survey_report.md
    comparison_table.csv
  scripts/
    extract_bibtex.py
  examples/
    good_review.md
```

一个 skill 可以包含：

```text
什么时候使用这个 skill
任务步骤
领域术语解释
输出模板
常见错误
验证清单
可调用脚本
示例输入输出
```

例如在你的研究场景里，可以有：

```text
video-dataset-auditing-skill
sonar-simulation-analysis-skill
paper-reading-skill
experiment-reporting-skill
latex-writing-skill
```

我的建议是：**优先沉淀 skill，而不是优先制造很多 agent。**
因为 skill 更容易复用、版本控制、测试和共享；agent 数量太多之后容易出现职责重叠、路由混乱、成本升高和调试困难。

------

### 6. 规划与执行循环：Planner / Executor Loop

这是 agent 和普通 workflow 最大的区别之一。

典型循环是：

```text
接收目标
理解上下文
拆解任务
选择 skill/tool
执行动作
观察结果
更新状态
检查是否完成
必要时重试或换策略
生成最终结果
```

可以抽象成：

```text
while not done:
    plan_next_step()
    choose_tool_or_skill()
    execute()
    observe()
    update_state()
    verify()
```

不过生产系统不一定要让 LLM 完全自由规划。更稳妥的方式是：

```text
高风险流程：workflow 固定编排
中风险流程：agent 在有限步骤内决策
低风险流程：agent 自主探索
```

------

### 7. 状态与记忆：State / Memory

一个成熟 agent 至少需要三类状态：

```text
1. Working Memory：当前任务上下文
2. Session State：当前会话中的中间结果、用户偏好、已执行步骤
3. Long-term Memory：长期知识、用户偏好、项目资料、历史经验
```

Google ADK 相关文档也强调 session、state、memory 对 agent 的上下文连续性很重要。([Google Cloud](https://cloud.google.com/blog/topics/developers-practitioners/remember-this-agent-state-and-memory-with-adk?utm_source=chatgpt.com))

在工程上要注意：memory 不是越多越好。记忆系统需要：

```text
写入规则
读取规则
过期机制
冲突处理
隐私边界
可审计性
```

否则 agent 很容易被旧信息污染，或者把不该持久化的信息写入长期记忆。

------

### 8. 权限与安全边界：Guardrails / Permissions

这是生产级 agent 的关键。

应区分操作风险等级：

```text
只读操作：搜索、读取文档、查询数据库
低风险写操作：生成草稿、创建临时文件
中风险操作：修改代码、调用内部 API、创建工单
高风险操作：发邮件、删文件、付款、部署、改数据库
```

成熟 agent 应该有：

```text
工具权限控制
用户确认机制
输入输出过滤
数据脱敏
提示注入防护
沙箱执行
审计日志
失败回滚
```

OpenAI Agents SDK 也把 guardrails、handoffs、structured outputs 作为 agent 运行行为的一部分。([OpenAI](https://openai.github.io/openai-agents-python/agents/?utm_source=chatgpt.com))

------

### 9. 多 Agent 协作与 Handoff

不是所有项目都需要 multi-agent。只有当任务天然存在清晰职责分工时，才建议拆成多个 agent。

例如：

```text
ResearchAgent：负责调研
CodingAgent：负责实现
ExperimentAgent：负责跑实验
ReviewAgent：负责检查结果
ReportAgent：负责写作
```

handoff 是 agent 把任务交给另一个专长 agent 的机制。OpenAI Agents SDK 文档也将 handoffs 描述为 agent 向其他专长 agent 委派任务的方式。([OpenAI](https://openai.github.io/openai-agents-python/handoffs/?utm_source=chatgpt.com))

但要避免这样设计：

```text
一个摘要 agent
一个翻译 agent
一个写作 agent
一个格式化 agent
一个检查 agent
```

这种拆分通常过细。很多时候它们只是同一个 agent 的不同 skills。

更合理的判断标准是：

```text
如果只是“不同能力”，做成 skill。
如果是“不同目标、不同权限、不同状态、不同责任边界”，才做成 agent。
```

------

### 10. 评估、观测与版本管理：Evaluation / Observability / Versioning

没有 eval 的 agent 很难进入生产。

至少要记录：

```text
输入
调用了哪些 tools/skills
中间步骤
工具返回结果
最终输出
耗时
成本
失败原因
用户反馈
```

还要有测试集：

```text
单轮任务测试
多轮任务测试
工具调用测试
异常输入测试
越权操作测试
提示注入测试
回归测试
```

每个 agent、skill、tool 都应该有版本号。例如：

```text
ResearchAgent v1.3
paper-survey-skill v0.8
search_papers_tool v2.1
```

这样出了问题才能回溯：到底是模型变了、prompt 变了、skill 变了，还是工具接口变了。

## 3. 我推荐的项目分层架构

一个比较成熟的 AI 项目可以这样分层：

```text
User / External System
        ↓
Orchestrator / Router
        ↓
Agent
  ├── Role & Policy
  ├── Planner
  ├── Memory
  ├── Skill Registry
  ├── Tool Registry
  ├── Guardrails
  ├── Evaluator
  └── Output Formatter
        ↓
Tools / APIs / Databases / Files / Web / Code Runtime
```

其中：

```text
Agent 负责决策
Skill 负责能力沉淀
Tool 负责真实动作
Workflow 负责确定性流程
Orchestrator 负责路由和调度
Guardrails 负责安全与合规
Evaluator 负责质量验证
```

## 4. 一个简单判断准则

你可以在项目中用下面这套标准：

### 应该做成 skill 的情况

```text
任务可重复
流程相对稳定
需要沉淀专家经验
不需要独立长期状态
不需要独立权限系统
可以被多个 agent 复用
```

例如：

```text
“读取论文并提取方法、数据集、指标、实验设置”
“根据实验日志生成报告”
“按照公司模板生成 PPT”
“根据代码规范检查 PR”
```

### 应该做成 agent 的情况

```text
有独立目标
需要多步规划
需要维护状态
需要选择工具/技能
需要处理失败和重试
需要独立权限边界
需要对最终结果负责
```

例如：

```text
“自动完成一次论文调研”
“管理一个代码修复任务”
“执行一轮实验并分析结果”
“处理一个客户工单直到关闭”
```

### 应该做成 workflow 的情况

```text
流程固定
风险较高
需要强可控性
每一步都能明确编码
不希望模型自由决策
```

例如：

```text
“上传文件 → 解析 → 入库 → 生成摘要 → 人审 → 发布”
```

## 5. 最推荐的实践原则

我会采用这条原则：

```text
少建 agent，多沉淀 skills；
低风险用 agent，高风险用 workflow；
agent 负责选择与协调，skill 负责专业能力，tool 负责动作执行。
```

也就是说，一个成熟系统不应该是：

```text
100 个 agent 到处互相调用
```

而更应该是：

```text
少数几个职责清晰的 agent
+ 一组高质量 skills
+ 一组强类型 tools
+ 明确 workflow
+ 完整 guardrails 和 eval
```

这样系统才更容易调试、复用、评估和上线。

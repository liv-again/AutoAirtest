# PC 分支 8 个既有测试失败修复设计

## 背景

LLM 缓存命中率修复完成后，全量测试结果为 `152 passed, 8 failed, 2 warnings`。
对 8 个失败逐项复现并追溯提交历史后，确认它们均已存在于 PC 分支基线，
不是本次 LLM 缓存改动引入的新回归。

失败来自测试契约没有同步后续架构和规则演进：

1. 设备执行已从编排器直接创建 Airtest/Poco 适配器迁移到 `DeviceWorkflow`。
2. `EvidenceRecollector` 已接收并复用设备工作流中的适配器。
3. 规划解释依据现在可能包含导航路径等多条记录，列表顺序不再代表语义类型。
4. 导航技能更新后，同一业务描述产生的动作数发生合理变化。
5. 元素顺序验证已改为相对顺序匹配，允许预期实体之间出现额外界面字段。

## 目标

- 保持当前 `DeviceWorkflow` 架构，不恢复已移除的编排器级适配器接口。
- 保持“相对顺序匹配、无需相邻”的正式验证规则。
- 更新过时测试，使其验证稳定的行为契约，而不是内部实现顺序或历史动作数量。
- 修正顺序验证主路径与证据冲突检测路径之间的语义不一致。
- 使 8 个目标测试及全量测试全部通过，且不影响已完成的 LLM 缓存修复。

## 非目标

- 不重构设备执行框架。
- 不改变规划动作生成规则或导航技能内容。
- 不恢复顺序验证中的严格全量列表匹配。
- 不增加仅供测试使用的生产接口或兼容层。
- 不修改 LLM 请求、提示词、解析、缓存遥测或重试行为。

## 方案选择

采用“保持当前生产契约，迁移过时测试，并修复一处规则一致性问题”的方案。

不采用以下方案：

- 恢复旧生产行为：会倒退 `DeviceWorkflow` 架构，并违反正式的相对顺序规则。
- 增加旧接口兼容层：会在生产代码中长期保留重复契约和测试专用分支。

## 详细设计

### 1. 设备执行测试

`tests/test_orchestrator_device_mode.py` 不再替换
`autoairtest.orchestrator.AirtestAdapter` 和 `PocoAdapter`。测试改为在
`DeviceWorkflow` 边界注入工作流实例，工作流内部使用假 Airtest/Poco 能力完成
动作并生成证据。

`tests/test_orchestrator_session_outputs.py` 中的假工作流遵循当前最小公开契约：

- 提供 `execute_plan(plan, case_dir)`。
- 提供供证据补采复用的 `poco` 和 `airtest` 属性。

与证据补采无关的测试可通过配置把补采次数设为 `0`，使测试边界更聚焦。

### 2. 证据补采测试

假 `EvidenceRecollector` 的构造函数接受当前参数：

- `max_attempts`
- `poco`
- `airtest`

测试除验证补采轨迹外，还应确认设备模式下传入的是工作流持有的同一组适配器，
从而覆盖“验证阶段复用设备连接”的生产契约。

### 3. 解释依据输出测试

不再使用 `rationales[0]` 假设别名解释始终位于首位。测试按
`interpretation_type == "navigation_alias"` 选择记录，再验证：

- `original_expression == "自选"`
- `normalized_meaning == "我的自选"`

这保留了原业务断言，同时允许导航路径依据按需增加或调整顺序。

### 4. 步骤预算测试

不再硬编码历史动作数 `4`。测试从本次运行写出的执行计划读取实际动作数，并验证：

- 动作数确实大于 `max_steps_per_case`。
- 执行结果为单个 `step_budget` 阻断记录。
- 阻断说明中的动作数与执行计划一致。
- 说明包含配置的预算值。

因此导航规则增加或减少合理步骤时，预算行为测试不会产生无关失败。

### 5. 相对顺序诊断契约

顺序验证的结构化详情保留：

- `expected`
- `observed`
- `filtered_for_order`
- `missing`
- `evidence_source`

额外界面文本不再作为 `unexpected` 错误，因为正式规则允许预期实体之间夹有其他
字段。缺少预期实体仍产生 `verification_evidence_gap`。

### 6. 顺序证据冲突一致性

当前 `_verify_order` 会先过滤非预期文本再判断相对顺序，但 `_order_status` 仍把
任何额外文本判定为 `gap`。这会导致 Poco 与 OCR 观察到相同预期相对顺序、仅附加
文本不同的情况下，被误判为冲突证据。

`_order_status` 改为与 `_verify_order` 使用相同规则：

1. 空预期返回 `uncertain`。
2. 按出现次数识别缺失实体；重复预期必须有对应数量的观察记录。
3. 任一预期实体缺失时返回 `gap`。
4. 过滤非预期文本。
5. 通过逐项消费观察序列判断相对顺序，避免 `list.index()` 对重复实体的假阳性。
6. 预期实体相对顺序正确时返回 `pass`。
7. 相对顺序错误时返回 `fail`。

## 测试策略

### TDD 回归测试

先增加一个失败测试：Poco 文本包含额外字段、OCR 文本只包含预期字段，但两者的
预期实体相对顺序相同；期望不产生证据冲突并通过顺序验证。

确认该测试因 `_order_status` 的旧严格行为失败后，再实施最小生产修复。
代码审查阶段再增加重复预期实体回归测试，确认单次观察不能满足重复预期，并以
相同的红—绿过程修正主验证与冲突检测路径。

### 契约迁移测试

更新 8 个既有失败测试，使其对应本设计中的当前契约。测试修改本身不改变生产行为。

### 验证层级

依次运行：

1. 新增顺序冲突回归测试，完成红—绿验证。
2. 8 个原失败测试。
3. 设备工作流、编排器、规划依据、验证规则相关测试集。
4. `python -m compileall -q autoairtest`。
5. 全量 `python -m pytest -q`。
6. `git diff --check` 和工作树状态检查。

## 风险与控制

- **测试掩盖真实回归**：每项断言仍围绕外部行为和产物，而非简单删除断言。
- **设备假对象偏离生产接口**：假对象只实现当前被编排器消费的最小公开契约。
- **顺序规则变化影响冲突检测**：新增回归测试覆盖 Poco/OCR 附加文本差异场景，
  并保留缺失实体与顺序错误的既有测试。
- **影响 LLM 缓存修复**：本次不修改任何 LLM 请求与解析代码，全量测试用于最终
  回归确认。

## 验收标准

- 8 个指定失败全部通过。
- 新增顺序冲突回归测试通过，并完成可证明的红—绿循环。
- 相关测试集全部通过。
- 全量测试为零失败。
- Python 编译检查与 `git diff --check` 通过。
- 工作树仅包含本设计范围内的已提交改动。
